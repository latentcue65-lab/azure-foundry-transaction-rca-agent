# Interview explanation and demo

“I built a transaction investigation agent registered in Microsoft Foundry. The model chooses read-only tools to inspect application logs, a payment HTTP API and historical SQLite events. Python validates customer scope, correlates exact trace and attempt IDs, preserves evidence, and validates the final RCA. When evidence is incomplete, the agent states uncertainty instead of inventing a cause.”

**Suggested demo.** Start the application with `uv run rca serve --mode foundry --with-mock`. Select TX9001. Show a database audit record, an actual HTTP retrieval and the corresponding application log. Explain that the wallet balance at decision time was INR 50 against INR 125 requested. The failure propagates through the payment response to checkout. Inspect the source references and exact six-field JSON.

Next select TX9005. A failed attempt and a successful retry have different trace IDs but share an explicitly mapped business transaction. The correct report explains recovery and does not present the whole transaction as still failed. Select TX9003 to show that an upstream timeout does not establish an underlying provider or database cause. Select TX9007 to show contradictory evidence handling.

If Azure is unavailable, explicitly start replay mode and describe it as a deterministic integration test. It still performs real file, database and HTTP I/O, but its text and decisions are not generated by an LLM. Do not present replay as proof of the Foundry requirement.

**Why is this agentic?** In live mode the model selects tools and follow-up identifiers from observations. The application constrains the permitted actions and budgets. A single investigator can satisfy this requirement; adding agents is not required for agency.

**Why keep correlation in Python?** Exact identity joins should be reproducible. The LLM interprets joined observations and explains cause; it should not invent a customer's transaction mapping. `causedByEventId` supplies explicit causal references where the synthetic source records have them. A common trace ID or close timestamps alone does not prove causation.

**Why SQLite?** The assessment asks for a lightweight local database and a direct connection. The adapter opens SQLite in read-only mode and executes predefined parameterized SQL. Historical audit attributes live in an `events` table. The agent cannot execute arbitrary SQL.

**Why an HTTP mock?** The assessment explicitly permits Mocki or another mock API tool. The bundled server is separately runnable and the adapter makes a real HTTP request. A hosted Mocki endpoint can use the same JSON payload and adapter without code changes.

**What runs in Azure?** The versioned agent definition and model execution. The laptop executes custom function calls and returns tool outputs to the same Foundry conversation. The UI is local. Registering an agent is different from hosting the entire application.

**How are hallucinations handled?** Source IDs, excerpts, times and ownership are validated against the local evidence registry. Complete findings require complete source coverage and no detected terminal conflict. One repair attempt is allowed. Unsupported results become an explicit incomplete finding. These checks establish reference integrity and selected consistency rules; semantic causal accuracy also needs reviewed model evaluations.

**Failure handling.** HTTP timeouts, malformed source data, page limits, unknown tools and invalid arguments are recorded. Repeated model/tool calls are bounded. Empty observations do not imply success. Model failures never silently become replay results. No tool changes a balance, retries a payment or performs remediation.

**Code walkthrough sequence:** request models → scope resolution → agent definition → executor loop → source tools → evidence/correlation → report validation → API/audit. Show the tests for scope isolation, retries and fabricated evidence, then the live mode-labelled evaluation results when Azure access is configured.
